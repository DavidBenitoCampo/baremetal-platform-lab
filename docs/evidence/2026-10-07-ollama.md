# Ollama on the Raspberry Pi

Date: 7 October 2026

I deployed Ollama on my single-node K3s cluster and tested inference with
Qwen2.5 0.5B. I then deleted the Ollama Pod and checked whether the replacement
used the downloaded model without another pull.

The serving and model persistence checks passed. The first generated answer
was wrong. These are separate results.

## Setup

- Raspberry Pi 5, 8 GB RAM.
- ADATA SU650 512 GB SATA SSD connected over USB.
- Ubuntu Server 24.04.5 LTS, ARM64. Root filesystem: `/dev/sda2`, ext4.
- K3s: `v1.36.5+k3s1`.
- Ollama API version: `0.40.0`. Configured image: `ollama/ollama:0.40.0`.
- Namespace: `ai-lab`. Deployment: `ollama`, one replica.
- Model cache: `ollama-cache`, a Bound PVC requesting 20 GiB from `local-path`.
- Service: ClusterIP, port 11434.
- Workstation access: `127.0.0.1:11435`, forwarded to the Service's port 11434.

The model list reported `qwen2.5:0.5b`, 397 MB, ID `a8b0c5157701`.
The inference records captured the full model digest:

```text
a8b0c51577010a279d933d14c2a8ab4b268079d44c5c8830c0a93900f1827c67
```

I have not recorded the container image digest or checked the PVC's host
directory with `findmnt` yet.

## Request conditions

I ran the probe from my workstation through the port-forward. The probe sent
requests sequentially. I did not run a concurrent load test.

The prompt was:

```text
Explain a Kubernetes readiness probe in one short sentence.
```

Every recorded request used:

- `num_ctx`: 2048.
- `num_predict`: 64, the requested output token limit.
- `num_thread`: 2.
- `num_gpu`: 0.
- `temperature`: 0.
- `seed`: 7.
- `keep_alive`: 5 minutes.
- `stream`: false.
- Socket timeout: 180 seconds.

`loaded_before` records model residency before each request. An unloaded model
does not mean an empty operating system file cache.

## Inference results

All five recorded requests returned HTTP 200 and completed with `ok: true`.

| Record | Loaded before | Wall time, seconds | Model load, seconds | Output tokens | Generation tokens/second |
| --- | --- | --- | --- | --- | --- |
| First request | No | 4.4195 | 2.388379 | 27 | 24.387 |
| Follow-up 1 | No | 4.2769 | 2.384060 | 27 | 24.690 |
| Follow-up 2 | Yes | 1.7685 | 0.003986 | 37 | 23.200 |
| Follow-up 3 | Yes | 1.7113 | 0.003936 | 37 | 23.147 |
| After Pod replacement | No | 4.3745 | 2.384996 | 27 | 25.045 |

Wall time covers the complete non-streaming inference request. Generation
tokens/second excludes model loading. I did not measure time to first token.

The two requests with the model already loaded finished in 1.71 to 1.77
seconds. Their output contained 37 tokens, compared with 27 tokens for the
unloaded requests. This was a small sequential test, not a throughput benchmark.

## Answer quality

The first response described a readiness probe as a check of the Kubernetes
cluster through Pod and Service monitoring. This is incorrect.

A readiness probe checks whether a container is ready to serve requests. Pod
readiness affects whether Kubernetes sends Service traffic to the Pod.

The two loaded requests produced a different answer from the first request,
despite using the same prompt, temperature, and seed. I kept the original
responses in the JSONL files. I have not run a broader accuracy evaluation.

## Pod replacement

Before deletion:

```text
Pod: ollama-76f6f79d6-v5jgm
Model: qwen2.5:0.5b
Model ID: a8b0c5157701
Size: 397 MB
```

I deleted only the Ollama Pod:

```bash
kubectl delete pod -n ai-lab -l app.kubernetes.io/name=ollama
```

The Deployment created `ollama-76f6f79d6-zxmpt`. I observed the replacement
as `1/1 Running`, with zero restarts, at a Pod age of nine seconds. I did not
record the deletion and readiness timestamps, so nine seconds is not a measured
recovery time.

The replacement listed the same model ID and size. I did not run another model
pull. After restarting the port-forward, inference returned HTTP 200 with the
same full model digest. The model loaded into memory again and the request
finished in 4.3745 seconds.

This verifies model persistence across Pod replacement while the node and
storage stayed available. This was not a backup restore or a node failure test.
I did not continuously probe the API during replacement, so downtime is unknown.
